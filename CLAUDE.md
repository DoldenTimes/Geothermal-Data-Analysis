# CLAUDE.md: natural-state data interpretation for geothermal model calibration

## 1. Ground rules

- **Ignore `README.md`.**
- **`Baseline/` is read-only.** Read all input data from it. Never edit, move, rename or write anything inside it.
- **Ignore `Logs/`.**
- **Where files go.** Scripts go in `Scripts/`. Every output goes in one of two folders under `Output/` (§5):
  - `Output/Calibration_Input/` holds only what the person or agent calibrating the model needs: the report, the target tables, the standard figures and their index. Someone who opens only this folder must be able to set up the calibration.
  - `Output/Additional_Output/` holds everything else: supporting checks, intermediate tables, extra figures, logs and the process log.

  Write nothing loose in `Output/`. When unsure where a new file belongs, put it in `Additional_Output/`.
- **Scope is the natural state only.** Production, injection and future scenarios are out of scope. Production and injection records may be used only to test whether the surveys represent the natural state (§4.1).
- **Audience.** Write every output for a reservoir engineer, or another agent, who will calibrate the natural-state model. Each finding should end in something they can act on: a target, a weight, a structural feature the model needs, or a data problem to resolve.
- **Defaults are binding in the standard columns.** Where this file defines a method, a threshold or a figure layout, the standard column or standard figure must use it exactly. If you think another method is better, add it as an extra column (for example `water_level_alt_mRL`) or an extra figure, and explain it in the report. Never replace the default.
- **Process log.** Write `Output/Additional_Output/process_log.md` by hand; it is the only output not generated by the script. It must contain:
  - the user's prompt, verbatim;
  - a summary of this file's rules as they were applied;
  - every step taken, including errors found and how they were fixed;
  - the full output of the acceptance check (§7), with an explanation of every WARN;
  - any departure from these instructions, with the reason.
- **Previous runs.** Earlier results may be deleted from the working tree but still exist in git history and on other branches. Do not restore or reuse them as inputs. Start from `Baseline/`.
- **No dataset knowledge is assumed.** These instructions name the *kinds* of input, not the files, wells, dates or values. Find out what this dataset contains before you analyse it (§2.1).

## 2. Inputs

### 2.1 Inventory first
Before any analysis, list everything under `Baseline/` and assign every file or directory one of the roles below. Write the result to `Output/Additional_Output/input_inventory.csv`, with columns `role, path, note`:
- `path` is relative to the repository root. A directory row covers everything inside it.
- Every file under `Baseline/` must be covered by some row. Use `out_of_scope` for anything you will not read, such as production or forecast models.
- Record any role you cannot fill, and any file whose role is unclear, in the process log.

The acceptance check (§7) reads the model geometry and well-block paths from this file.

- **Model properties are not evidence.** Never present a property of the reference model, such as permeability, heat flux, upflow location or rock conductivity, as if the data showed it.
- **Describing the starting model is allowed.** You may describe the reference model so the engineer can see how far the data are from it. Label that content clearly as "[reference model]".
- **State any assumption you need.** If you need a parameter that is not in the data, for example rock thermal conductivity to turn a gradient into a heat flux, state the assumed value and where it came from, tagged `[assumption]`.
- **Report provenance.** Read every source, comment and quality field in the data files and report what they say, including any labels that bear on how far the data can be trusted.

## 3. Input file formats

These describe how the information is stored. They are not findings, and they do not replace the integrity checks in §4.1. Confirm each one against the files, and record in the process log any that does not hold.

- **Model grid file (`geometry_dat`).** The file is in MULgraph format.
  - **Layer section:** each line is `index  bottom_elevation  centre_elevation` (mRL). Line 0 gives the top surface. Layer *i* runs from the bottom of layer *i*−1 down to its own bottom, so the layers tile the grid with no gaps.
  - **Surface section:** gives the ground-surface elevation of each column. `model_surface_mRL` is the column's value in this section. It is **not** the top of a layer or of the block that contains the wellhead. If a column has no entry, use the top of the grid (layer line 0) and say so.
  - Parse the sections by whitespace, not by fixed width.
  - Block names are the column name followed by the layer number.
- **Well-to-block file (`well_blocks_json`).** For each well it holds:
  - the blocks along the track, each with an elevation interval;
  - the block or blocks of each feed zone, in feed-zone order;
  - interpolation weights.

  Survey-point and feed-zone blocks must match it (§7, checks G1 and G2). If your own point-in-polygon search disagrees with it, find out why before you use either.
- **Well data files (`well_data_json`).**
  - Some list entries are stored as strings, for example `"[top, bottom, 'QUALITY']"`. Parse them with a literal evaluator, not by hand.
  - Feed-zone top and bottom may be labelled "m", but they are elevations in mRL.
  - Survey dictionaries are keyed by date, then by elevation stored as a string.
- **Plain-column files (`well_data_dat`).**
  - Survey files are two columns, `value elevation_mRL`.
  - Transient files are two columns, time in years since a reference date and value. Establish the reference date by matching the series against the JSON, and record it.
  - File names do not always follow one pattern; match files to wells by content and name. Report any irregular names.
- **Mapping file (`mapping`).** River and shoreline entries may be lists of separate segments (ragged arrays). Fault entries are single polylines. Use the feature names as given in the file.

## 4. Required analysis steps

### 4.1 Data integrity and timing
1. **Cross-check sources.** Compare the JSON with the plain-column files for every T, P and transient point. Check that:
   - every survey point and feed zone lies within the well track;
   - every feed zone lies within the slotted or open interval;
   - the casing and liner design is consistent with the track.
2. **Test whether the surveys represent the natural state.**
   - For each well with a pressure gauge, compare the survey pressure, interpolated to the gauge elevation, with the **first** transient value. Note when each gauge series starts relative to the well's own first production or injection, and relative to the first production anywhere in the field.
   - **The gauge comparison decides the verdict, not the date label.** If a survey matches a pre-production gauge reading to within the reading precision, it represents the natural state, whatever date it carries. Report a date label that conflicts with the gauge test as a data question. It is not a reason to downgrade the verdict.
   - **Injectors.** A survey taken during or soon after injection usually shows an isothermal section near the injectate temperature (derive it from the injectate enthalpy and state how). A profile colder than the injectate, with no such section, is evidence *against* an injection-affected survey. Where the formation is hotter than the injectate, injection cooling could be hidden, so lower the confidence.
   - **Wells without a gauge.** Compare their feed-zone pressures with the pressure trend of the wells that passed the gauge test, at the same elevations.
   - **Assign verdict and confidence with this rubric** (first matching row wins):

     | Evidence | Verdict | Confidence |
     |---|---|---|
     | Survey matches a pre-production gauge reading within the reading precision | natural state | high |
     | Injector whose formation is hotter than the injectate (cooling could be hidden) | probably natural state at best | low |
     | Gauge test misses by more than the precision, but feed-zone pressures lie on the verified trend within the tolerance | probably natural state | medium (record the miss as a data question) |
     | No pre-production gauge reading (no gauge, or the series starts after production), and feed-zone pressures lie on the verified trend within the tolerance | probably natural state | medium |
     | Feed-zone pressures off the trend by more than the tolerance, or a profile signature of injection or production | possibly disturbed | low |

     **Tolerance:** 3 bar, or twice the RMS residual of the gauge-verified feed zones about their trend, whichever is larger. State the value used. Give the reason for each well's verdict in the report. Use the same `ns_verdict` and `ns_confidence` for a well in every output file (in `pressure_consistency_check.csv` they are the `verdict` and `confidence` columns).
   - Carry the confidence through to the target weights using the default factors in §5. **If every well gets the same confidence, the factor changes no relative weight; justify that explicitly in the report.**

### 4.2 Wellbore physics: read the profiles correctly
- **Pressure.** Measured pressure represents the formation only at feed zones. Elsewhere it follows the fluid column inside the well, which pivots at the dominant feed zone. Use pressure at feed zones as the formation pressure targets. Do not treat the shallow wellbore column, for example about 1 bar at the wellhead, as reservoir pressure.
- **Temperature.** Between feed zones in open hole, internal flow in the well can distort temperature, for example by producing isothermal sections. Behind casing, temperatures are usually closer to the conductive formation temperature. Before interpreting any feature as a reservoir feature, consider whether the well itself could have caused it.
- **Inversions and isothermal sections.** Interpret temperature inversions, isothermal sections and boiling-point-for-depth sections physically: lateral outflow, cold downflow, or two-phase conditions. Locate each one against the casing shoe and the feed zones.
- **Isothermal section (definition).** A run of consecutive survey points spanning ≥ 300 m whose temperatures all lie within 5 °C of each other. Apply it to open hole only.

### 4.3 Thermodynamics
- **Use IAPWS-IF97.** Use Region 4 for saturation temperature and pressure, and Region 1 for liquid density (and enthalpy if needed).
  - **Do not use the Kell polynomial, or any fit only valid below 150 °C,** at reservoir temperatures.
  - Above the critical pressure (220.64 bar) there is no Tsat. Leave the boiling margin blank there, and do not plot a clamped Tsat curve.
- **Validate your implementation.** Check it against the IF97 verification tables and the reference values Tsat(1.01325 bar) = 99.97 °C and Tsat(100 bar) = 311.0 °C. Make the script fail if any error exceeds 0.1 K.
- **Hydrostatic checks.** Use these definitions so that runs can be compared:
  - Test only single-phase liquid intervals: boiling margin ≥ 10 °C and P ≥ 1.5 bar throughout.
  - **Window algorithm.** Within each eligible interval, build windows from the top downward. Close a window at the first feed zone or casing shoe reached once the window is ≥ 300 m long; otherwise keep extending it. A final remnant shorter than 300 m joins the window above it. Windows do not overlap.
  - Compare the measured ΔP with ΔP integrated through IF97 Region 1 density over the measured T profile, with g = 9.80665 m/s². Report the ratio, the implied density and the rounding uncertainty.
  - Report results in two bands for each well, as well as overall:
    - **cased:** the window bottom is at or above that well's production casing shoe;
    - **open:** the window top is below the shoe.
  - A **cold well** has Tmax < 100 °C. Report the cold-well median ratio, per band, as the field-wide component, and present it as a possible datum or convention issue, not as physical overpressure. Then report each well's excess above that component.
  - Before calling any gradient physically impossible, check:
    - a datum offset (it cannot change a gradient);
    - a gravity or unit convention (it would act at every depth);
    - two-phase fluid (it would make the column lighter, not heavier);
    - rounding.
- **Boiling margin.** Report Tsat(P) − T at every point, and flag every interval where it is below about 5 °C.

### 4.4 Interpretation for calibration

**Shared definitions.**
- Compute every per-well characteristic from that well's rows in `NS_calibration_targets.csv`, ordered from the top down. The acceptance check recomputes them from that table (check D1).
- A survey point is **liquid-filled** if P ≥ 1.5 bar and boiling margin ≥ 0. Points above the critical pressure, where the margin is blank, count as liquid-filled.
- All fits are ordinary least squares of T (or P) against elevation. Report gradients as positive when temperature increases with depth.
- An **isotherm crossing** is the first pair of consecutive points (top down) with T above < X ≤ T below. Interpolate its elevation linearly. Leave it blank if there is no such pair.

Produce at least the following, with the definitions given, so that runs can be compared:
- **Per-well characteristics** (`well_summary.csv`, columns in §5):
  - maximum temperature and its elevation (the shallowest, if tied);
  - temperature and elevation at total depth (the deepest survey point);
  - **inversion:** going down, track the running maximum. The inversion is the largest drop of T below it, if that drop is at least 3 °C. Its top is the elevation of the running maximum, and its base is the elevation of the point with the largest drop. Leave all three blank if there is no drop of 3 °C;
  - **shallow gradient:** fit over the shallowest liquid-filled point and every liquid-filled point within 300 m below it. Require ≥ 3 points; otherwise leave blank;
  - **deep gradient:** fit over every point at or below (inclusive) the deeper of the inversion base and the deepest feed-zone bottom. If there is neither, use every point. Require ≥ 3 points spanning ≥ 300 m; otherwise leave blank. Report `deep_fit_n` and `deep_fit_span_m` as extra columns;
  - elevations of the 100 °C and 200 °C isotherm crossings;
  - **minimum boiling margin** over liquid-filled points only, and its elevation;
  - **water level:** fit P against elevation through the three shallowest liquid-filled points. The water level is where that line reaches 1.01325 bar. Report `water_level_extrapolation_m` (distance above the top survey point) as an extra column;
  - **pivot:** the dominant feed zone is the one with the highest quality tag; break ties by thickness, then by depth (the deeper wins). Report its mid elevation and the survey pressure there;
  - **regime**, by the first rule that matches:
    1. **two-phase** if any liquid-filled point has a boiling margin ≤ 1 °C;
    2. **recharge/downflow** if Tmax < 100 °C;
    3. **outflow** if the inversion is ≥ 10 °C;
    4. **upflow** if Tmax ≥ 200 °C and there is no inversion;
    5. otherwise **conductive**.

    Add an extra column `near_boiling` (true where the minimum boiling margin is < 5 °C). It does not change the regime. If you disagree with a rule-based regime, say so in `regime_note`, not in `regime`;
  - natural-state verdict and confidence (§4.1).
- **Lateral structure.** T and P at common elevations, and at model layer centres. Use interpolation only and never extrapolate. Show this with the standard plan-view and section figures (§8).
- **Conceptual model, built from the data alone.** Show the following in the standard conceptual-model figure (§8, F6):
  - where the upflow is;
  - the paths, depths and directions of outflow;
  - recharge and downflow areas;
  - the extent and thickness of the cap;
  - any two-phase zone;
  - how deep pressures are connected across the field.

  Relate each feature to the faults and surface water in the mapping file, and state which observation supports each claim. Where the data cannot decide between two explanations, say so and state what observation would decide it.
- **Feed zones.** Give survey T, P and boiling margin at each feed zone, its model block, and its quality tag.

### 5.5 Weighting
- `weight` is the temperature weight: the location weight multiplied by the natural-state confidence factor.
- `weight_P` is the pressure weight. **It is non-zero only at feed zones**, where it equals the feed-zone quality factor multiplied by the confidence factor.
- In `feedzones.csv`, `weight_T` is the feed zone's location weight from the table below (normally 1.0) multiplied by the confidence factor, and `weight_P` is as above.
- Justify any departure from the defaults below in the report.

Apply the first row that matches, in this order:

| Location of the point | Temperature weight |
|---|---|
| Above the model surface | 0 |
| Within 30 m of the wellhead, or in the top block of its column | 0.3 |
| Feed zone | 1.0 |
| Behind casing | 0.5 |
| Open hole within an isothermal section (§4.2; possible internal flow) | 0.5 |
| Open hole | 0.8 |

| Natural-state confidence | Factor |
|---|---|
| high | 1.0 |
| medium | 0.75 |
| low | 0.5 |

| Feed-zone quality tag | Factor for `weight_P` |
|---|---|
| highest tag in the dataset | 1.0 |
| intermediate tag | 0.8 |
| lowest tag, or any tag that is not a quality grade | 0.5 |

State in the report which tags were found and how each was mapped.

## 6. Report structure (`Calibration_Input/NS_data_interpretation.md`)

1. **Key conclusions for calibration.** Numbered. Each one names the observation that supports it and ends with a line starting `**Action:**`.
2. **The data.** What exists (from the input inventory), how it was checked, and its provenance labels. Includes the natural-state timing verdict for each well and figure F7.
3. **Temperature structure.** Includes a well-by-well table and figures F2, F3 and F4.
4. **Pressure structure.** Includes a table at common elevations, the hydrostatic results by band, and the pressure versions of F3 and F4.
5. **Conceptual model.** Figure F6, plus a numbered table that gives, for each element in the figure, the supporting observation and its claim type.
6. **Recommended calibration set-up.** Targets and weights. Where heat and mass need to enter and leave. The permeability structure the data imply. Boundary requirements.
7. **Data quality issues and open questions.** Rank them by how much they affect calibration.
8. **Output file index.** Two lists, one per output folder.

**Report hygiene.**
- Tag every claim with exactly one of `[obs]`, `[interp]`, `[assumption]` or `[reference model]`. Do not use other spellings.
- Embed every standard figure with a relative link (`figures/<file>.png`) and a caption that states what it shows, the elevation or section line, and its claim type.
- The report must contain no unfilled template text, such as `{name}` or `nan`.
- A value stated in the text must match the table it comes from, including categorical values such as the regime.

## 7. Quality bar and acceptance check

- **Run the acceptance check after the final run:** `python Scripts/check_deliverables.py --rerun`. It checks:
  - the input inventory (I1);
  - required files in their folders, required figures, and the figure index (F1, F2, F3);
  - required columns and table structure (S1, S2) and file formats (S3);
  - survey-point and feed-zone blocks against the well-to-block file (G1, G2);
  - layer centres against the grid file's layer section, and that no value is extrapolated (G3);
  - `model_surface_mRL` against the grid file's surface section (G4);
  - Tsat against an independent IF97 Region 4, and the boiling margins (T1, T2);
  - the §4.4 definitions, recomputed from the targets table (D1);
  - the weight rules, and that natural-state confidence agrees across files (W1, W2, W3);
  - that the numbers in the report appear in the output tables, that the script writes the report, and that no template text remains (R1, R2, R4);
  - that a clean re-run reproduces every table and the report (R3);
  - the process log (P1).

  **Do not finish with any FAIL.** Fix the cause in the analysis script, not in the check. Explain every WARN in the process log.
- **Every number in the report comes from an output file** written by the script. Check the report against those tables before finishing.
- **Look at every figure** after it is generated, against its checklist in §8. Confirm that it renders and is readable, and that the labels sit on their wells.
- **Use plain units consistently** throughout: mRL, bar, °C, kJ/kg, kg/s.
- **Label the strength of each claim** with the tags in §6. Distinguish observations ("well X reaches T °C at z mRL") from interpretations ("lateral outflow").
- **Never present an anomaly as fact before checking it.** If something looks physically impossible, such as a gradient steeper than a column of water, first check for a datum, unit or wellbore explanation, and report what you found. **This applies equally to anomalies in the model geometry:** if your result disagrees with the well-to-block file or the layer section, assume your own code is wrong until you have shown otherwise.
- **Geometry self-check.** Before finishing, compare each geometric value with its source and record the result in the process log:
  - model surface against the surface section;
  - blocks against the well-to-block file;
  - layer centres against the layer section;
  - wellhead elevation against the first track point.
- **Independent review before finishing.** Re-read each key conclusion and each data-quality issue against the tables, and try to disprove it. Record in the process log what you changed as a result.

## 8. Standard figures

Every run produces the same figure set, with the same layout, in `Output/Calibration_Input/figures/`. An engineer can then read any run's figures without relearning them, and runs can be compared side by side. Extra figures are welcome in `Output/Additional_Output/figures/`, but they do not replace these.

### 8.1 House style (applies to every figure)

- **One base layer for every plan view:**
  - model grid columns, as thin light-grey lines;
  - model extent, dashed;
  - faults, black, labelled with their names from the mapping file;
  - water bodies, blue;
  - wellheads, as black dots;
  - well tracks, as grey lines.

  Use equal aspect ratio, a scale bar, and easting and northing in m.
- **One colour per well**, assigned in `well_groups` order and used in every figure.
- **Fixed colour scales.** Temperature: one perceptually uniform sequential colormap with limits 0 to the field Tmax rounded up to the next 50 °C, the same in every figure. Differences (deviation from the field median, or later model minus data): diverging, red = hotter, blue = colder, centred on zero.
- **Fixed elevation axis.** All profile and section panels share one elevation range: the highest wellhead to the deepest survey point, rounded outward to 100 m.
- **Fixed isotherms:** 50 °C apart, with 100 °C and 200 °C drawn heavier (they match `z_100C_mRL` and `z_200C_mRL`).
- **Data are points; derived curves are lines.** Survey points are markers. Tsat(P), fits and isotherms are lines. Never draw a line through measured points without also showing the points.
- **No data, no colour; data envelope fully coloured.** Never contour, shade or colour outside the data envelope (§8.2, F4). Inside it, every section fills the envelope with colour on the fixed scale (temperature: 10 °C steps; pressure deviation: diverging, 1 bar steps, centred on zero), with contour lines drawn on top. Contour lines alone are not enough. Hatch all areas without data light grey and label them "no data" (in the legend or on the panel). Leave the air above the model surface white, not hatched. The only exception is the interpolated companion set (§8.4), which lives in `Additional_Output/figures/` and is labelled as interpolation.
- **Interpretation looks different from observation.** Draw interpretive elements, such as arrows and inferred boundaries, dashed or outlined, and key them to the conceptual-model table (§6). Reference-model content appears only in separate figures in `Additional_Output/figures/` whose title starts with "[reference model]".
- **Layout.** Legends sit outside the data area. Labels sit on their wells and do not overlap. Use at least 150 dpi. Every title gives what is shown, the elevation or section line, and the units.

### 8.2 The seven standard figures

| ID | File(s) in `Calibration_Input/figures/` | Purpose |
|---|---|---|
| F1 | `well_map.png` | Base map: where everything is, and where the sections run |

**F1. Base map.** The base layer (§8.1), with every well labelled at its wellhead. Draw every section line used in F4 and F6, with its end labels (for example A and A′). If the well groups are spatial, outline them lightly.
*Check:*
- the grid is visible;
- every fault and water body from the mapping file is present and named;
- every label sits on its well;
- the section lines are labelled.

**F2. Well profiles.**
- `profile_<well>.png` has an inset locator map beside two panels that share the elevation axis. The locator map is the base layer, with this well highlighted in its colour and the others grey.
  - **Temperature panel:** survey points; Tsat(P) as a line, with none drawn above 220.64 bar; the casing shoe as a horizontal line labelled "shoe"; feed zones as shaded bars labelled with their quality tag; the model surface and wellhead as labelled horizontal lines; the 100 °C and 200 °C crossings; and intervals with boiling margin < 5 °C shaded.
  - **Pressure panel:** survey points, feed-zone pressures as larger markers, the pivot and the water level.
  - **Legend:** the survey date and the natural-state verdict and confidence.
- `profile_panels_<group>.png` shows small multiples: one temperature panel per well in the group, all with the same axes (§8.1). One locator map shows every well in the group in its colour.

*Check:*
- the axes are identical across panels;
- the shoe, feed zones and surface are present;
- no Tsat line is drawn above the critical pressure.

**F3. Elevation-band symbol maps.** One panel per elevation band, each drawn on the base layer.
- **Bands:** 500 m thick, aligned to multiples of 500 mRL, from the shallowest to the deepest band that holds data from at least three wells.
- **Wells with data in the band:** plot each at its track position at the band's mid elevation. Colour and size its symbol by `T_minus_field_median_degC` in fixed classes: a cross for within ±10 °C; circles of increasing size for 10–20, 20–30, 30–40 and > 40 °C, red for hotter and blue for colder.
- **Wells with no data in the band:** small open grey circles.
- Print the field median for the band in the panel title.

The pressure version uses `P_minus_trend_bar`, the deviation from the hydrostatic trend of gauge-verified feed zones, in classes of 2 bar. The values come from `Additional_Output/T_P_at_elevation_bands.csv`. This layout shows the lateral pattern without inventing values between sparse wells, and the same layout can later show model-minus-data residuals.
*Check:*
- every symbol sits on its well track at that depth;
- the classes match the legend;
- open circles mark missing data.

**F4. Data section.** Choose the line through the two hottest wells (by Tmax) and extend it to the model extent; add more lines if useful. State the line's end coordinates in the report. Include wells within 500 m of the line, or a stated distance, projected onto it, and print each well's offset. Draw:
- the model surface along the line;
- each projected well track, labelled at its bottom, with casing shoe and feed zones marked;
- the survey points coloured by temperature, on the fixed scale;
- the data envelope: between neighbouring wells that both have data at that elevation, never below either well's deepest point and never above its shallowest. Fill it with colour interpolated linearly between the two wells, on the fixed temperature scale (§8.1), and outline it with a thin dotted line;
- isotherms at the fixed levels, contoured on top of the fill, only inside the data envelope;
- everything outside the envelope (and below the model surface) hatched light grey, labelled "no data";
- intervals with boiling margin < 5 °C, stippled;
- faults and water bodies that cross the line, as labelled ticks along the top edge where they cross.

State the vertical exaggeration. The pressure version (`section_<line>_P.png`) is drawn the same way, filled and contoured with the deviation from the hydrostatic trend on the diverging scale.
*Check:*
- the whole envelope is colour-filled, not only contoured;
- nothing is coloured outside the envelope, and the no-data area is hatched and labelled;
- offsets are printed;
- surface features are labelled where they cross the line.

**F5. P–T state.** All survey points on P against T, coloured by well. Add the IF97 saturation curve, the critical point, and feed zones as larger markers.
*Check:*
- the saturation curve stops at the critical point;
- feed zones are distinguishable.

**F6. Conceptual model.** Two panels:
1. a plan view on the base layer;
2. a section on the same line as F4, with F4's colour-filled envelope, isotherms and no-data hatching as the background.

Use this fixed symbology, and show its legend even for elements that are absent:

| Element | Symbol |
|---|---|
| Deep hot upflow | red upward arrow |
| Lateral outflow | orange horizontal arrow at its depth |
| Cold recharge or downflow | blue arrow |
| Cap (low-permeability, conductive gradient) | grey band, with top and base elevations labelled |
| Two-phase or near-boiling zone | stipple |
| Isotherms (100 °C, 200 °C) | from F4 |

Draw an arrow solid only where a measured feature supports it directly, for example an inversion at that depth in a well on the line. Draw it dashed where it is inferred. Number every element and key it to the conceptual-model table in the report (§6, section 5), which gives the supporting observation and the claim type.
*Check:*
- every arrow is numbered and listed in the table;
- solid and dashed are used as defined;

**F7. Gauge check.** One panel per gauged well. Plot the transient pressure against time from the first reading over a stated period, and draw:
- the survey pressure interpolated to the gauge elevation, as a horizontal line labelled with the survey date;
- a band of ± the reading precision around the first reading;

Print the verdict and confidence in each panel title.
*Check:*
- both the first reading and the survey value are visible;
- the production lines are at the dates in `pressure_consistency_check.csv`.

### 8.3 Optional reference-model companion

If useful to the engineer, draw the reference model's temperatures on the F4 line, with the same scale and axes, as `Additional_Output/figures/section_<line>_reference.png`. Title it "[reference model]" and mark the data envelope from F4 on it. It shows where the data and the starting model differ. It is never evidence.

### 8.4 Interpolated companion figures (required)

The standard figures colour only the data envelope. To give the engineer a whole-field picture as well, every run also produces an interpolated companion set in `Output/Additional_Output/figures/`. It is never placed in `Calibration_Input/`, never listed in `figures_index.csv`, and never used as a target or as the only support for a conclusion.

| File | Content |
|---|---|
| `section_<line>_interpolated.png` | One per F4 line: temperature on that line |
| `section_<line>_P_interpolated.png` | One per F4 line: deviation from the hydrostatic trend on that line |
| `maps_temperature_interpolated.png`, `maps_pressure_interpolated.png` | Plan views, one panel per F3 elevation band, of the F3 quantities `T_minus_field_median_degC` and `P_minus_trend_bar` |

Fixed method, so that runs can be compared:
- **Interpolation:** linear, on a Delaunay triangulation of the data. In sections, triangulate every survey point by its distance along the line and its elevation. In plan views, triangulate the wells' band values at their track positions at mid-band (as in F3). A band panel with fewer than three wells shows symbols only.
- **No extrapolation:** colour only inside the convex hull of the data. Hatch everything outside it light grey and label it "no data". Leave the air above the model surface white.
- **Same scales and layout** as the matching standard figure: the same colour scales, elevation axis, base layer, isotherms (on the temperature sections), labels and section-line ends.
- **Show the data:** overlay every survey point (sections) or well symbol (plan views) as markers, and outline the F4 data envelope with a dashed line, so that interpolation across long gaps is visible.
- **Label it as interpolation:** each title starts with "[interpolated, not data]". The legend states the method and that colours outside the dashed envelope are not constrained by neighbouring wells.

In the report, show these figures in sections 3 and 4 as links to `../Additional_Output/figures/`, with a caption tagged `[interp]`, and list them in the output file index. Do not quote any value read from them.
*Check:*
- nothing is coloured outside the convex hull of the data;
- the F4 envelope is outlined and the data are shown;
- every title starts with "[interpolated, not data]".
