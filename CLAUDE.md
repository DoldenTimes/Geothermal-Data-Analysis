# CLAUDE.md: natural-state data interpretation for geothermal model calibration

## 1. Ground rules

- **Ignore `README.md`.**
- **`Baseline/` is read-only.** Read all input data from it. Never edit, move, rename or write anything inside it.
- **Ignore `Logs/`.**
- **Scripts go in `Scripts/`.** Data outputs, figures and reports go in `Output/`, with figures in `Output/figures/`.
- **Scope is the natural state only.** Production, injection and future scenarios are out of scope. Production and injection records may be used only to test whether the surveys represent the natural state (§4.1).
- **Audience.** Write every output for a reservoir engineer, or another agent, who will calibrate the natural-state model. Each finding should end in something they can act on: a target, a weight, a structural feature the model needs, or a data problem to resolve.
- **Process log.** Write `Output/process_log.md` by hand; it is the only output not generated by the script. It must contain:
  - the user's prompt, verbatim;
  - a summary of this file's rules as they were applied;
  - every step taken, including errors found and how they were fixed;
  - the full output of the acceptance check (§7), with an explanation of every WARN;
  - any departure from these instructions, with the reason.
- **Previous runs.** Earlier results may be deleted from the working tree but still exist in git history and on other branches. Do not restore or reuse them as inputs. Start from `Baseline/`.
- **No dataset knowledge is assumed.** These instructions name the *kinds* of input, not the files, wells, dates or values. Find out what this dataset contains before you analyse it (§2.1).

## 2. Inputs

### 2.1 Inventory first
Before any analysis, list everything under `Baseline/` and assign every file or directory one of the roles below. Write the result to `Output/input_inventory.csv`, with columns `role, path, note`:
- `path` is relative to the repository root. A directory row covers everything inside it.
- Every file under `Baseline/` must be covered by some row. Use `out_of_scope` for anything you will not read, such as production or forecast models.
- Record any role you cannot fill, and any file whose role is unclear, in the process log.

The acceptance check (§7) reads the model geometry and well-block paths from this file.

### 2.2 Roles: what counts as data and what counts as reference

| Role (`role` value) | What it is | How to use it |
|---|---|---|
| `well_data_json` | Per-well data files: track, casing/liner design, feed zones, downhole T and P surveys, transient pressures, flow records | **Data** (factual) |
| `well_data_dat` | Plain-column copies of the well data | **Data, cross-check only.** Compare with `well_data_json`; do not use as a primary source |
| `mapping` | Polylines of faults, rivers, lakes and other surface features | **Data** |
| `well_groups` | The list of wells and their groupings | **Data** |
| `geometry_dat` | The model grid file | **Geometry only:** the vertex, grid, layer, surface and well-track sections |
| `well_blocks_json` | Well-to-model-block intersections | **Geometry only.** This is **the authority for block assignment** |
| `reference_rock` | Rock types and permeabilities of the reference model | **Reference only, never evidence** |
| `reference_bc` | Boundary conditions of the reference model (heat flux, upflows, rain, surface water) | **Reference only, never evidence** |
| `reference_results` | Model results and initial conditions | **Reference only, never evidence** |
| `reference_other` | Model set-up and configuration files, parameter sets, plotting files (these may hold hard-coded paths from another machine) | **Reference only, never evidence** |
| `out_of_scope` | Production, injection and forecast models, and anything else not needed | Do not read |

- **Model properties are not evidence.** Never present a property of the reference model, such as permeability, heat flux, upflow location or rock conductivity, as if the data showed it.
- **Describing the starting model is allowed.** You may describe the reference model so the engineer can see how far the data are from it. Label that content clearly as "[reference model]".
- **State any assumption you need.** If you need a parameter that is not in the data, for example rock thermal conductivity to turn a gradient into a heat flux, state the assumed value and where it came from.
- **Report provenance.** Read every source, comment and quality field in the data files and report what they say, including any labels that bear on how far the data can be trusted.

## 3. Input file formats

These describe how the information is stored. They are not findings, and they do not replace the integrity checks in §4.1. Confirm each one against the files, and record in the process log any that does not hold.

- **Model grid file (`geometry_dat`).** The file is in MULgraph format.
  - **Layer section:** each line is `index  bottom_elevation  centre_elevation` (mRL). Line 0 gives the top surface. Layer *i* runs from the bottom of layer *i*−1 down to its own bottom, so the layers tile the grid with no gaps.
  - Parse the sections by whitespace, not by fixed width.
  - Block names are the column name followed by the layer number.
- **Well-to-block file (`well_blocks_json`).** For each well it holds:
  - the blocks along the track, each with an elevation interval;
  - the block or blocks of each feed zone, in feed-zone order;
  - interpolation weights.

  Survey-point and feed-zone blocks must match it (§7, checks G1 and G2). If your own point-in-polygon search disagrees with it, find out why before you use either.
- **Well data files (`well_data_json`).**
  - Some list entries are stored as strings, for example `"[top, bottom, 'QUALITY']"`. Parse them with a literal evaluator, not by hand.
  - Feed-zone top and bottom may be labelled "m", but they are elevations in mRL.
  - Survey dictionaries are keyed by date, then by elevation stored as a string.
- **Plain-column files (`well_data_dat`).**
  - Survey files are two columns, `value elevation_mRL`.
  - Transient files are two columns, time in years since a reference date and value. Establish the reference date by matching the series against the JSON, and record it.
  - File names do not always follow one pattern; match files to wells by content and name. Report any irregular names.
- **Mapping file (`mapping`).** River and shoreline entries may be lists of separate segments (ragged arrays). Fault entries are single polylines. Use the feature names as given in the file.

## 4. Required analysis steps

### 4.1 Data integrity and timing
1. **Cross-check sources.** Compare the JSON with the plain-column files for every T, P and transient point. Check that:
   - every survey point and feed zone lies within the well track;
   - every feed zone lies within the slotted or open interval;
   - the casing and liner design is consistent with the track.
2. **Test whether the surveys represent the natural state.**
   - For each well with a pressure gauge, compare the survey pressure, interpolated to the gauge elevation, with the **first** transient value. Note when each gauge series starts relative to the well's own first production or injection, and relative to the first production anywhere in the field.
   - **The gauge comparison decides the verdict, not the date label.** If a survey matches a pre-production gauge reading to within the reading precision, it represents the natural state, whatever date it carries. Report a date label that conflicts with the gauge test as a data question. It is not a reason to downgrade the verdict.
   - **Injectors.** A survey taken during or soon after injection usually shows an isothermal section near the injectate temperature (derive it from the injectate enthalpy and state how). A profile colder than the injectate, with no such section, is evidence *against* an injection-affected survey. Where the formation is hotter than the injectate, injection cooling could be hidden, so lower the confidence.
   - **Wells without a gauge.** Compare their feed-zone pressures with the pressure trend of the wells that passed the gauge test, at the same elevations.
   - Give each well a verdict (natural state, probably natural state, or possibly disturbed) and a confidence (high, medium or low), with the reason. Carry the confidence through to the target weights using the default factors in §5. **If every well gets the same confidence, the factor changes no relative weight; justify that explicitly in the report.**

### 4.2 Wellbore physics: read the profiles correctly
- **Pressure.** Measured pressure represents the formation only at feed zones. Elsewhere it follows the fluid column inside the well, which pivots at the dominant feed zone. Use pressure at feed zones as the formation pressure targets. Do not treat the shallow wellbore column, for example about 1 bar at the wellhead, as reservoir pressure.
- **Temperature.** Between feed zones in open hole, internal flow in the well can distort temperature, for example by producing isothermal sections. Behind casing, temperatures are usually closer to the conductive formation temperature. Before interpreting any feature as a reservoir feature, consider whether the well itself could have caused it.
- **Inversions and isothermal sections.** Interpret temperature inversions, isothermal sections and boiling-point-for-depth sections physically: lateral outflow, cold downflow, or two-phase conditions. Locate each one against the casing shoe and the feed zones.

### 4.3 Thermodynamics
- **Use IAPWS-IF97.** Use Region 4 for saturation temperature and pressure, and Region 1 for liquid density (and enthalpy if needed).
  - **Do not use the Kell polynomial, or any fit only valid below 150 °C,** at reservoir temperatures.
  - Above the critical pressure (220.64 bar) there is no Tsat. Leave the boiling margin blank there, and do not plot a clamped Tsat curve.
- **Validate your implementation.** Check it against the IF97 verification tables and the reference values Tsat(1.01325 bar) = 99.97 °C and Tsat(100 bar) = 311.0 °C. Make the script fail if any error exceeds 0.1 K.
- **Hydrostatic checks.** Use these definitions so that runs can be compared:
  - Test only single-phase liquid intervals: boiling margin ≥ 10 °C and P ≥ 1.5 bar throughout.
  - Use **non-overlapping** windows at least **300 m** long. Split them at feed zones and at the casing shoe where the 300 m minimum allows.
  - Compare the measured ΔP with ΔP integrated through IF97 Region 1 density over the measured T profile, with g = 9.80665 m/s². Report the ratio, the implied density and the rounding uncertainty.
  - Report results in two bands for each well, as well as overall:
    - **cased:** the window bottom is at or above that well's production casing shoe;
    - **open:** the window top is below the shoe.
  - A **cold well** has Tmax < 100 °C. Report the cold-well median ratio, per band, as the field-wide component, and present it as a possible datum or convention issue, not as physical overpressure. Then report each well's excess above that component.
  - Before calling any gradient physically impossible, check:
    - a datum offset (it cannot change a gradient);
    - a gravity or unit convention (it would act at every depth);
    - two-phase fluid (it would make the column lighter, not heavier);
    - rounding.
- **Boiling margin.** Report Tsat(P) − T at every point, and flag every interval where it is below about 5 °C.

### 4.4 Interpretation for calibration
Produce at least the following, with the definitions given, so that runs can be compared:
- **Per-well characteristics** (`well_summary.csv`, columns in §5):
  - maximum temperature and its elevation;
  - temperature and elevation at total depth;
  - inversion: the largest drop below a running maximum, if it is at least 3 °C. Give its size, top and base;
  - **shallow gradient:** a least-squares fit over the top 300 m of the liquid-filled survey;
  - **deep gradient:** a least-squares fit below both the inversion base and the deepest feed zone. Leave it blank if that interval is under 300 m;
  - elevations of the first downward crossings of the 100 °C and 200 °C isotherms;
  - minimum boiling margin and its elevation;
  - estimated water level (state the method; it extrapolates above the top survey point);
  - pivot pressure and elevation at the dominant feed zone (state the rule for choosing it);
  - regime: upflow, outflow, conductive, recharge/downflow, or two-phase;
  - natural-state verdict and confidence (§4.1).
- **Lateral structure.** T and P at common elevations, and at model layer centres. Use interpolation only and never extrapolate. Show this as maps at several elevations, plus at least one cross-section through the hottest wells.
- **Conceptual model, built from the data alone.** Show the following in a sketch:
  - where the upflow is;
  - the paths, depths and directions of outflow;
  - recharge and downflow areas;
  - the extent and thickness of the cap;
  - any two-phase zone;
  - how deep pressures are connected across the field.

  Relate each feature to the faults and surface water in the mapping file, and state which observation supports each claim. Where the data cannot decide between two explanations, say so and state what observation would decide it.
- **Feed zones.** Give survey T, P and boiling margin at each feed zone, its model block, and its quality tag.

**Weighting.**
- `weight` is the temperature weight: the location weight multiplied by the natural-state confidence factor.
- `weight_P` is the pressure weight. **It is non-zero only at feed zones**, where it equals the feed-zone quality factor multiplied by the confidence factor.
- Justify any departure from the defaults below in the report.

| Location of the point | Temperature weight |
|---|---|
| Feed zone | 1.0 |
| Open hole | 0.8 |
| Open hole within an isothermal section ≥ 300 m long (possible internal flow) | 0.5 |
| Behind casing | 0.5 |
| Within 30 m of the wellhead, or in the top block of its column | 0.3 |
| Above the model surface | 0 |

| Natural-state confidence | Factor |
|---|---|
| high | 1.0 |
| medium | 0.75 |
| low | 0.5 |

| Feed-zone quality tag | Factor for `weight_P` |
|---|---|
| highest tag in the dataset | 1.0 |
| intermediate tag | 0.8 |
| lowest tag, or any tag that is not a quality grade | 0.5 |

State in the report which tags were found and how each was mapped.

## 6. Report structure (`NS_data_interpretation.md`)

1. **Key conclusions for calibration.** Numbered. Each one names the observation that supports it.
2. **The data.** What exists (from the input inventory), how it was checked, and its provenance labels. Includes the natural-state timing verdict for each well.
3. **Temperature structure.** Includes a well-by-well table.
4. **Pressure structure.** Includes a table at common elevations and the hydrostatic results by band.
5. **Conceptual model.** A sketch, plus a description.
6. **Recommended calibration set-up.** Targets and weights. Where heat and mass need to enter and leave. The permeability structure the data imply. Boundary requirements.
7. **Data quality issues and open questions.** Rank them by how much they affect calibration.
8. **Output file index.**

## 7. Quality bar and acceptance check

- **Run the acceptance check after the final run:** `python Scripts/check_deliverables.py --rerun`. It checks:
  - the input inventory;
  - required files, figures and columns;
  - survey-point and feed-zone blocks against the well-to-block file;
  - layer centres against the grid file's layer section, and that no value is extrapolated;
  - Tsat against an independent IF97 Region 4, and the boiling margins;
  - the weight rules;
  - that the numbers in the report appear in the output tables;
  - that the script writes the report;
  - that a clean re-run reproduces every table.

  **Do not finish with any FAIL.** Fix the cause in the analysis script, not in the check. Explain every WARN in the process log.
- **Every number in the report comes from an output file** written by the script. Check the report against those tables before finishing.
- **Look at every figure** after it is generated. Confirm that it renders and is readable, and that the labels sit on their wells.
- **Use plain units consistently** throughout: mRL, bar, °C, kJ/kg, kg/s.
- **Label the strength of each claim.** Distinguish observations ("well X reaches T °C at z mRL") from interpretations ("lateral outflow").
- **Never present an anomaly as fact before checking it.** If something looks physically impossible, such as a gradient steeper than a column of water, first check for a datum, unit or wellbore explanation, and report what you found. **This applies equally to anomalies in the model geometry:** if your result disagrees with the well-to-block file or the layer section, assume your own code is wrong until you have shown otherwise.
- **Independent review before finishing.** Re-read each key conclusion and each data-quality issue against the tables, and try to disprove it. Record in the process log what you changed as a result.
